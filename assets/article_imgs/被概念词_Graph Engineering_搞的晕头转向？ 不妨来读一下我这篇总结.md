> 2026 年 7 月 18 日，Peter Steinberger（@steipete，PSPDFKit 创始人）在 X 上发了一句调侃：「Are we still talking loops or did we shift to graphs yet?」这条推文在 48 小时内引爆社区。"Graph Engineering（图工程）"瞬间从一个小圈子的说法变成了 AI 工程的新热词。

> 但你只要认真去查，就会发现这个词的含义 **极度发散** ：有人指知识图谱，有人指 Agent 编排，还有人指一种"以关系为中心"的工程视角。

> 所以这篇指南的目标不是给你"图工程的准确定义"——那东西不存在。目标是给你 **一把尺子** ，让你下次再听到"Graph Engineering"时，能立刻判断对方在说哪一层、针对什么问题、以多大动态性在谈。

# 一、最浅的一层：图就是点和边

在聊任何"工程"之前，先回到图本身。

图（graph）就是 **点（节点）+ 线（边）** 。这不是什么高深的东西——你见过的每一张公司组织架构图、每一个家族族谱、每一条地铁线路图，都是图。1736 年欧拉解决"柯尼斯堡七桥"问题时，脑子里想的也不是"我要发明图论"，而是"这几座桥之间到底连不连得上"。

从第一天起，图的威力就是回答 **"连不连得上、怎么连、连多远"** ，而不是"单个东西长什么样"。

用公司的例子说：你的 HR 系统里每个员工是一行记录（表格思维），擅长回答"公司有多少人、平均工资多少"。但如果有人问"张三请病假了，谁能顶他？顶他的人又请假了呢？"——这就不是表格擅长的了，这是在问关系网络。你得顺着"张三→所在项目组→备用负责人→备用负责人的项目组"走两层甚至三层。这就是图问题。

Graph Engineering = 把"关系"当作一等公民，系统性地设计、存储、查询、计算、治理这些关系的工程学科。

它不是某个具体工具，而是一种视角的切换：从"东西是什么"转向"东西之间怎么连"。就像一个公司，单看每个部门的职能说明书什么也看不出来；但如果你画出汇报线、协作线、资源流动线，整个组织的运行逻辑一下子就清楚了。

# 二、为什么需要图：表格思维的极限

传统系统以 **表** 为中心，这没什么不好——表擅长聚合统计。但有一类问题它天生吃力：

谁和谁 **间接** 相关？（二度、三度人脉）

一笔欺诈怎么 **藏在网络** 里？（A→B→C→D 看似无关，链起来是洗钱）

一个故障 **影响扩散** 到哪？

这个任务失败了 **该退回哪一步** ？

这些问题有一个共同点：它们都在问"顺着关系追"，而不是"数单个东西"。图天生适合回答它们。

有一个业内经典事故值得记住。某电商推荐系统（占营收 30%）宕机了 6 个小时。根因是什么？是一条"找和你相似的人买过的相似商品"的图查询——看起来无害，但在热门品类里，它爆发性地遍历了几十亿个节点。 **不懂图算法就会写出这种会炸的查询。** 这就像一个公司，财务知道每个部门的预算（表格），但没人画过"一个预算削减决策会沿着哪些协作线影响哪些项目"的图，结果一刀切下去才发现断了关键链路。

所以图工程不是"要不要用图数据库"的技术选型问题，而是"你的系统里有没有一类问题是关于关系的"的设计问题。如果有，你就需要图的视角；如果没有，别为了时髦硬上。

# 三、数据图工程：最古老的一层

"图工程"最早不是 AI 圈的词，而是数据工程领域的。从底到顶，它有一套完整的生命周期：

| 层 | 干什么 | 典型东西 |
|-|-|-|
| ① 基础 | 点+边；有向/无向、加权、可成环或 DAG | G=(V,E) |
| ② 建模 | 定义"谁是谁、什么连什么、怎么连" | 本体/Ontology、Schema、实体解析 |
| ③ 存储 | 把图存下来、查得快 | Neo4j、TigerGraph、JanusGraph、NebulaGraph |
| ④ 查询与算法 | 沿着边"走"和"算" | Cypher / Gremlin / GQL；PageRank、最短路径、社区发现 |
| ⑤ 图智能 | 让模型从结构里学 | GNN、图嵌入(Node2Vec)、GraphRAG |
| ⑥ 应用 | 落到业务 | 反欺诈、推荐、供应链、知识图谱 |

这里有一个经常被跳过但极其关键的步骤—— **实体解析** 。不同系统里"同一个人/公司"要被识别并合并成同一个节点，否则图就是一团重复的噪音。这就像公司并购后，两家公司的客户名单要合并去重：A 公司的"腾讯"和B 公司的"Tencent"是同一个实体，不合并就没法画出真实的商业关系网。

**四个最容易混的词** （看完才不会被热词忽悠）：

**图数据库 ≠ 知识图谱** ：图数据库是存储层（比如 Neo4j），它只是"存点存边、遍历快"；知识图谱额外有语义层——本体定义了"什么是公司、什么是投资关系、投资关系有哪些属性"，还能做推理。你可以用图库存知识图谱，但一个空的图库不等于知识图谱。

**知识图谱 ≠ GraphRAG** ：知识图谱是 **数据** ；GraphRAG 是"用图谱给 LLM 检索上下文"的 **套路** 。没有知识图谱的 GraphRAG 会退化成普通 RAG。

**GraphRAG ≠ Context Graph** ：Context Graph 把 LLM 踢出推理路径，走确定性遍历 + 溯源，用于金融/医疗等强合规场景。

**Graph Engineering（方法论）≠ LangGraph（框架）** ：LangGraph 是具体的运行时；graph engineering 是更上面的设计学科。

到这里，你已经知道了"图工程"在数据层面长什么样。但 2026 年人们疯狂讨论的"Graph Engineering"主要不是指这一层——而是 AI Agent 的图工程。这是接下来要讲的重点。

# 四、2026 的新含义：AI Agent 图工程

今年兴起的第二层意思，是 **把多 Agent 系统设计成一张显式图** 。

用公司类比来理解：在传统的多 Agent 系统里，几个 Agent 之间的协作是"隐式"的——它们在一个群里对话，谁该接话、谁该让路，全靠 prompt 和上下文"涌现"。这就像一个公司没有项目流程图，所有事情靠拉群解决——小团队可以，一旦项目复杂就会乱。

图工程的做法是把这些隐式关系 **显式化** ：

**节点（node）** = 一个 Agent，或一个确定性步骤（工具调用、审批门、评估器）。每个节点 **可被引擎执行、可产出结果** 。就像公司里的一个岗位——它有明确的职责，被叫到时就要交付。

**边（edge）** = **路由** ：顺序 / 条件分支 / 并行扇出 / 扇入。边同时承载控制流、数据流和共享状态。就像公司里项目流程图上的箭头——它定义了工作从谁手里流到谁手里。

**状态（state）** = 一个沿边流动、被各节点读写共享的对象。这和"把所有上下文塞进一条长 prompt"完全不同——就像公司的项目文档不是每次开会从头念一遍，而是有一份持续更新的项目文件，每个人看自己该看的部分、改自己该改的字段。

**图引擎 / 执行器** = 真正跑图的东西：提交任务后，引擎遍历节点、应用路由、维护共享状态；失败就重试 / 回滚到检查点 / 补偿。

一句话： **图是引擎，也是真相源。**

但这里有一条最重要的工程直觉，很多人会忽略： **图的最小原子不是 Agent，也不是 Node，而是一个完整的 Loop** ——动作→结果→检查→决定是否继续。原话很直白： **"你连一个稳定的循环都做不好，就不可能把十个不稳定循环连成一个可靠的图。"** 就像一个公司，如果一个员工连"接到任务→做完→自查→交付"这个循环都跑不稳，你把他放进任何项目流程里都只会制造混乱。

还有一个反直觉的点： **大多数节点不应该是 LLM** 。确定性任务（算时长、查 JSON、判预算）交给代码，模糊判断才交给模型。就像公司里不是每个岗位都需要"创造性判断"——出纳按规则数钱、质检员按清单打勾，这些确定性环节用代码比用大模型可靠得多。

那什么时候才值得上图？当你发现：交接总在长上下文里丢、不同阶段想用不同模型/权限、一个慢子任务卡住全部、第 7 步失败要从第 1 步重来——这些信号说明你的系统复杂度已经超过了"线性 prompt 链"的承载能力。

反过来， **"会判断不用图"比"会画图"更高级** 。不是所有协作都该建模成图，就像不是所有公司都需要复杂的矩阵式组织架构——十个人的团队用图编排就是杀鸡用牛刀。

# 五、三维框架：把发散的概念收拢成一把尺子

到这里，你已经看到了"图工程"至少有三种不同语境：数据层面的图（知识图谱/图数据库）、Agent 执行层面的图（LangGraph 那类）、以及更抽象的"以关系为中心的工程视角"。

如果只是记住这三种，你下次遇到"图工程"还是会晕——因为真正的混乱不在"有几种图工程"，而在于 **每个人说的"图工程"暗含了三个不同的维度** 。把它们拆开来，就是一把能消除绝大多数概念混乱的尺子：

> **Graph Engineering = Scope（图作用在哪个层级）× Plane（同一层级有哪些系统平面）× Dynamism（每个图有多"动态"）。**

![](https://feishu.cn/file/RKavbKl3KoL0Y3xIPnNcR6Mznrd)

这把尺子的用法是：每次看到"Graph Engineering"，先问三个问题——

```Plain Text
① 它说的是哪个范围（Scope）？   Work Graph（一次任务）还是 Org Graph（长期组织）？
② 它说的是哪个系统平面（Plane）？ Control / Execution / Evaluation / Adaptation / Governance？
③ 它说的是静态、动态生成，还是自适应修改（Dynamism）？
```

接下来三章分别把这三个维度讲透。每讲一个维度，我都会用公司场景来锚定直觉。

# 六、第一维 Scope：Work Graph vs Org Graph

explainx.ai 的文章做了一件非常聪明的事：它把图工程拆成 **两张不同的图** 。这一拆是理解整个范式的关键一跃——因为生产级的多 Agent 系统同时运行着既稳定又动态的两层。

![](https://feishu.cn/file/Qfckb6jOMoNj69xM5PocTwlrnah)



Work Graph：这一次目标怎么完成？

Work Graph 回答的是"这一次目标具体怎么完成？"。它的节点通常是任务、Agent 调用、工具调用、验证步骤、人工审批节点和中间产物。边表示依赖、数据传递、条件路由、重试和回退。

```Plain Text
用户目标 → 需求分析 ┬→ 市场调研
├→ 技术调研
└→ 竞品调研 → 结果汇总 → 验证 → 输出
```

用公司类比：这就是 **项目执行计划** 。公司接到了一个客户需求，项目经理把需求拆成若干子任务，安排给不同的人，定义谁先做谁后做、哪些可以并行、什么时候需要阶段汇报。项目结束了，这张执行计划就归档了——它是短生命周期的。

Org Graph：系统中长期存在哪些能力和责任？

Org Graph 回答的是"系统中长期存在哪些能力、角色、权限和责任关系？"。节点可能是长期 Agent、Agent Team、部门、服务、模型池、工具平台、人类角色。边表示汇报关系、授权关系、服务关系、能力依赖、协作协议和责任归属。

```Plain Text
制作总监 Agent ┬→ 剧本团队
├→ 互动设计团队
├→ 分镜团队
├→ 资产生产团队
└→ 质量与合规团队
```

用公司类比：这就是 **公司组织架构图** 。它定义了公司长期有哪些部门、每个部门负责人是谁、谁向谁汇报、哪些资源归谁管。它的生命周期比任何单个项目都长得多——项目来了又走，但组织架构不会因为一个项目结束就解散。

关键辨析：Org Graph 不是"更大的 Work Graph"

直觉上你可能觉得"Org Graph 就是把一个任务放大成一个组织"。但两者 **不是大小关系，而是语义不同** ：

Work Graph 描述的是： 要做什么 / 先做什么 / 后做什么 / 什么算完成

Org Graph 描述的是： 谁具有什么能力 / 谁拥有什么权限 / 谁长期负责什么领域 / 什么资源归谁管理 / 谁可以调用谁

举个例子：一个"安全 Agent"可能长期存在于 Org Graph 中——它是公司安全部门的员工，随时待命。但某次普通文案任务的 Work Graph 不会调用它，因为那不需要安全审查。反过来，一个 Work Graph 可能动态创建十个临时研究任务，但这十个任务不一定对应十个长期组织成员——就像公司为了一个项目临时雇了十个外包，项目结束后外包就走，但公司的组织架构没变。

桥接层：Assignment / Staffing Graph

那 Org Graph 是怎么变成 Work Graph 的？中间其实隐含一层—— **任务由谁来承担** 。更准确的生成关系是：

```Plain Text
Org Graph 提供能力池
↓ 根据目标进行 staffing / 能力选择（Assignment Graph）
↓ 实例化 Work Graph
↓ 把 Work Graph 节点分配给 Org Graph 中的角色或能力
```

用公司的话说：公司有常设的部门（Org Graph），接到项目后，项目经理从各部门抽人组成临时项目组（Assignment），项目组按照执行计划干活（Work Graph）。这层"抽人组队"的映射，是很多人画图时漏掉的中间环——他们要么只画组织架构图不画执行流程，要么只画执行流程不关心谁来做。

Dynamic Agent Org：图自己会变

explainx.ai 还提出了一个更激进的概念： **拓扑本身在工作发生时会改变** 。这就像一个公司不仅能临时组项目组，还能在项目进行中根据情况动态调整组织结构——发现新业务线就成立新部门、发现某条业务没前途就裁撤、发现某个外部供应商更优就把它纳入生态。

| 触发 | 图的响应 |
|-|-|
| 任务范围意外扩大 | spawn 新 Agent 节点，接入现有图 |
| 并行分支提前收敛 | 折叠汇合点，向前路由输出 |
| 不可恢复错误 | route 到 fallback 节点，向上游告警 |
| 优先级中途变化 | 重排 work graph 边，暂停低优先级节点 |

失败路由有一套标准动作： **retry the node / route to a fallback / escalate to a human checkpoint / abort the branch** 。最后这一项"人工检查点"——把人拉进来做决策——正是后面要讲的 CodexLoom 里 Needs You （需要你）机制的精神来源。

# 七、第二维 Plane：五个系统平面

知道了图可以作用在 Work 和 Org 两个层级，还不够。因为在同一层级内部，还藏着 **不同的控制问题** 。一个公司里，"把活干完"和"检查干得好不好"和"根据结果调整流程"和"控制预算和权限"，是完全不同的几件事。

同一范围内存在 **五个系统平面** 。Anthropic 会话推导的"四张嵌套图"正是这个维度的展开，这里把 **Control 单独成面** 补全成五个。

![](https://feishu.cn/file/VQidbyuPUozEiRxiHA1cX8run1g)

1. Control Plane（控制平面）——指挥

负责决定：如何拆分目标、创建哪些任务、谁执行、哪些可以并行、下一步走哪条边、何时暂停或终止。典型节点是 Planner / Router / Scheduler / Orchestrator。

用公司的话说，这就是 **项目经理** ：他不亲自写代码、不做设计、不跑测试，但他决定"先做哪个模块、后做哪个、谁来做、什么时候可以联调"。控制平面负责"指挥"，不一定亲自做业务。

2. Execution Plane（执行平面）——做出来

真正完成工作的地方：Agent 推理、工具调用、代码执行、文件处理、视频生成。控制平面说"做什么"，执行平面负责"做出来"。

这就是公司里 **干活的员工** ——程序员写代码、设计师画图、文案写文案。他们接收到的是明确的任务，交付的是具体产物。

3. Evaluation Plane（评价平面）——验收

判断：结果正确吗？满足目标吗？证据充分吗？可以进入下游吗？

评价本身也可能是一张图——就像公司里的质量保证流程，不是一个"通过/不通过"的开关，而是一套多维检查：

```Plain Text
产物 ┬→ 格式校验
├→ 事实校验
├→ 逻辑校验
├→ 安全校验
└→ 用户偏好评价 → 评价结果汇总 → 通过 / 修复 / 升级人工
```

评价 **不只发生在任务最终阶段** ，还可以发生在节点级、分支级、阶段级、项目级、甚至组织级。就像公司的质检不只发生在产品出厂，研发有代码评审、设计有方案评审、发布有灰度验证、上线后有用户反馈追踪。

这里有一条最值钱也最容易被忽视的工程直觉： **Verifier 是瓶颈** 。Worker 和 Verifier **绝不能共享上下文** ——如果验证者和执行者看的是同一份上下文，验证者会倾向于"理解"而不是"挑错"，就像让写代码的人自己 review 自己的代码，天然会放过自己的盲点。

4. Adaptation Plane（自适应平面）——学习

根据反馈修改未来的运行方式。修改对象分等级，从轻到重：

```Plain Text
Level 1：修改当前节点的 Context
Level 2：修改 Prompt 或 Playbook
Level 3：修改工具选择和模型选择
Level 4：修改当前 Work Graph 的节点和边
Level 5：修改 Work Graph 生成规则
Level 6：修改 Org Graph 的角色和能力结构
```

这里需要区分两个容易混淆的概念： **动态拓扑** （运行中增删重排任务）和 **自适应图** （有明确的学习闭环：观测→诊断→提修改→评估集验证→治理审批→发布新版本）。仅能运行时加节点，叫"动态生成"更合适；能基于长期反馈证明并部署改进，才接近"自适应"。

用公司类比：动态拓扑就像项目经理在项目进行中临时加了一个调研任务——这是灵活性。自适应就像公司在做了十个项目后发现"每次都要在后期加调研任务"，于是把"需求分析阶段必须包含竞品调研"写进了项目模板——这是从经验中学习了，并且制度化地改了流程。

> ACE 论文（ *Agentic Context Engineering* , arXiv:2510.04618）做的正是 **Level 2 的自改上下文 / Playbook** ——Generator→Reflector→Curator 三角色，把经验增量式更新进结构化手册，解决"上下文坍缩"。但它 **不是自改图的拓扑布线** 。真正的"图自修复"还需要更高层控制器：跑图→收集 Trace→诊断→提修改候选→沙箱验证→比较→发布。

5. Governance Plane（治理平面）——定边界

决定系统 **被允许做什么、做到什么程度** ：预算、权限、安全规则、人工审批、数据访问、风险等级、 **不可修改的 Anchor（锚点）** 、审计与责任归属。

用公司类比：这就是 **财务部 + 法务部 + 合规部** 。它们不关心你怎么把活干完，但它们关心你花了多少钱、用了什么数据、有没有违反安全规定。治理也可以动态执行——就像公司对不同风险等级的项目有不同的审批流程：

```Plain Text
低风险任务 → 自动执行、用低成本模型
高风险任务 → 增验证器、限工具权限、必须人工审批
预算即将耗尽 → 禁 Fan-out、切便宜模型、输出当前最佳
```

但有一条铁律： **治理图可以动态执行 ≠ 治理边界可以随意动态改变** 。评价图 + 治理图 **必须约束** 适应图，否则系统会为提分而悄悄改低评分标准——就像一个公司的质检部门如果归生产部门管，质检标准就会越来越松。

Anthropic 会话的最终结论点破了整个平面维度的本质： **"图工程之后不是更大的图，而是围绕图建立的评价 / 学习 / 治理控制平面。"** 也就是说，画一张执行图只是开始；真正让系统可靠运行的，是围绕这张图建立的评价、适应和治理控制回路。

# 八、第三维 Dynamism：图有多"动态"

这是最该单独抽出来的一维——因为很多人一听到"图工程"就默认"图必须是动态的、会自己改的"。但 **动态性不是 Graph Engineering 的必要条件** 。一个完全静态的 DAG 仍然属于图工程——就像一个公司就算流程完全固定不变，它还是需要一张流程图。

动态程度可以分四级，用公司的成熟度来类比最好记：

| 级 | 名称 | 说明 | 公司类比 |
|-|-|-|-|
| Level 1 | 静态图 | 设计时固定节点和边，所有任务始终走同一流程 | 创业初期：一套固定流程打天下，"先做需求→再开发→再测试→上线" |
| Level 2 | 参数化 / 条件图 | 结构基本固定，按条件走不同路径 | 成长期：有了标准流程但区分项目类型，"视频项目走 A 路径、文档项目走 B 路径" |
| Level 3 | 运行时生成图 | 根据当前目标动态创建 Work Graph | 成熟期：项目经理接到需求后，根据具体情况当场决定拆几个子任务、怎么排依赖 |
| Level 4 | 自适应、自修改图 | 基于历史表现修改图模板/节点/路由/验证，经评价和治理后发布 | 学习型组织：做了十个项目后发现规律，主动改流程模板，并且经过管理层审批后制度化 |

所以每次看到"Graph Engineering"，除了问"哪个范围"和"哪个平面"，还要追问第四个问题： **这张图是预先固定的？是条件选择的？是运行时生成的？还是能根据反馈自我修改的？**

这三个维度（Scope × Plane × Dynamism）问完，你对任何"Graph Engineering"的说法都能精确定位了。

# 九、理想参考架构：它是三维坐标里一格的展开

前面讲了那么多维度和框架，你可能想看一个"理想中完整的图工程系统"到底长什么样。社区流传的一份"Graph Engineering 理想参考架构"把"图即执行引擎"从一条推文展开成了一套设计语言。用三维坐标系看，它基本就是 **Work Graph × Execution** 那一格的展开。

![](https://feishu.cn/file/FAqfb98ELo9TCFxdrnlcxP9lnzd)

![](https://feishu.cn/file/HGVKbilLEoIBg2xRzGzcVrdRnGe)

| 区块 | 核心意思 |
|-|-|
| **I. OVERVIEW** | 系统不是线性流程，而是"实体+关系"的图。好处：并行推理、局部决策、全局一致、持续适应。 |
| **II. REFERENCE ARCHITECTURE** | 五层：User Goal → Graph Orchestrator（计划/路由/适应）→ Graph Components → Execution Layer → Observability & Feedback（信号喂回 Orchestrator 闭环）。 |
| **III. CORE PRINCIPLES** | 图优于线；局部决策+全局一致；组件可组合；冗余路径容错；可观测内建；图随反馈演化。 |
| **IV. TOPOLOGY PATTERNS** | 八种拓扑：Linear、Fan-out、Fan-in、Diamond、Loop、Hub & Spoke、Mesh、Hybrid。 |
| **V. GRAPH PRIMITIVES** | 九个原语：Node、Edge、State、Context、Memory、Tools、 **Router** 、 **Reducer** 、 **Verifier** 。 |
| **VI. GRAPH OPERATIONS** | Plan → Dispatch → Execute → Observe → **Adapt** 。最后一步是"更新图并重复"。 |
| **VII. EXECUTION FLOW EXAMPLE** | Diamond：Planner → Research×2 → Analysis/Visualization → Reducer → Verifier → Output。 |
| **VIII. OUTCOMES** | 按结构扩展、抗变化/失败、并行提效、可观测、适应新目标。 |

这张图描绘的是一个 **以图为执行引擎、能自我演化** 的系统——图不只是画出来看，而是真正负责计划、路由、执行、失败处理和自适应。其中九个原语里最该记住的三条： Router 决定流向， Reducer 聚合多路结果， Verifier 是质量的闸门。

它最值得注意的是 Observability 反馈回 Orchestrator 形成闭环——这是"活图"和"死图"的分水岭。如果你的图只是画出来挂在墙上（或只读投影），它就是死的；如果你的图会被观察、被修改、被重新执行，它才是活的。

# 十、用一张矩阵把三维统一起来

把 Scope（节点/Loop、Work Graph、Org Graph、跨组织图）× Plane（执行/评价/自适应/治理）铺成矩阵，Control 作为贯穿的调度层。这张矩阵就是三维框架的"全图视图"——每一格都是一个真实的设计问题：

| 范围 | 执行 | 评价 | 自适应 | 治理 |
|-|-|-|-|-|
| **节点 / Loop** | Agent 完成局部任务 | 判断本次完成没有 | 修改 Prompt/Context | 工具权限、重试预算 |
| **Work Graph** | 项目任务与依赖 | 节点/阶段/项目验收 | 动态增删节点、调整拓扑 | 项目预算、审批、风险限制 |
| **Org Graph** | 多团队长期协作 | 团队和能力表现评估 | 增减角色、调整职责能力 | 组织权限、资源配额、责任体系 |
| **跨组织图** | 不同系统协作 | 信任与结果认证 | 动态选择合作方 | 协议、身份、结算、合规 |

用公司语言把整张矩阵读一遍，你会发现它讲的是一个完整的故事：

**节点级** ：一个员工做完一件事，自查一下，改改自己的工作方式，在工具权限内操作。

**Work Graph 级** ：一个项目团队拆任务并行干活，在每个阶段做验收，根据情况动态调整计划，在项目预算和审批约束下运行。

**Org Graph 级** ：整个组织长期协作，定期评估各部门表现，据此增减角色和调整能力分配，在组织权限和责任体系框架下治理。

**跨组织级** ：多个组织协作时，要解决信任和结果认证问题，动态选择合作方，靠协议、身份认证和合规框架来约束。

# 十一、结合 CodexLoom：它处在图工程的哪一层

讲了这么多框架，来看看一个真实的工程案例。 **CodexLoom** 是 AgentTeam 最近开源的一个工程，建立在 OpenAI Codex 之上，定位是"长期领域 Agent 组织与治理平台"。它把一条 Codex 对话线程变成某个长期负责的 Domain Agent 的持续工作空间，再把多个 Agent 组织成能互相协作、对外沟通、接受人类治理的团队。

用三维尺子量一下它，可以非常精确地说清楚它在图工程坐标系里的位置：

![](https://feishu.cn/file/TJWRbAFyeodYzYxGxEqcXCown8c)

Scope 维——它是认真的 Org Graph，但不做 Work Graph：

在 Org Graph 这一侧它做得很强。每个 Agent 绑定一条长期 Codex Thread，有稳定身份、Profile、累积的上下文记忆和负责领域——这就是 Zone ownership 和 Preserved memory。Agent 之间的关系通过 organization-links.json 显式声明，权限和治理规则通过 Relationship / Permission / Anchors 定义。这些是 Org Graph 的标准组件，它都认真实现了。

但在 Work Graph 这一侧，它几乎是空白的。Agent 之间的协调靠有界 Messages 和 Topics——这是一种消息账本式的协作，不是拓扑执行。没有任务级自动 Verifier，没有 Dynamic Agent Org 的拓扑自改写。

Plane 维——Execution 和 Governance 强，Evaluation 和 Adaptation 缺失：

Execution 层面，每个 Agent 线程就是一个带记忆的持久执行节点， internal/hub 的 sendTaskWithTopic 负责把消息派到对应线程——这相当于一个 Router。Governance 层面，它有 Artifact（受管产物交接）和 Needs You（请求人类决策）机制，相当于审批门和不可修改事实的 Anchor。这两层是它的核心价值。

但 Evaluation 层面没有图级自动 Verifier——质量检查靠人工 Needs You。Adaptation 层面也没有图级自修复布线——Topic 的 brief 可以更新，但那是协调记录，不是拓扑演化。

Dynamism 维——Level 1 到 2：

最硬的证据在代码里。 internal/hub/collaboration_group.go 第 14 行注释直接写了： CollaborationGroup is a named, shared view over explicit collaboration relationships. It has no routing, permission, execution, or context effects. 手册也明言 **"Graph 是 read projection"** ——Team 三图（Organization / Collaboration / Activity）是 React Flow 渲染的只读投影，不运行时生成、不自适应。

**准确结论** ：CodexLoom 不是一个"半成品图引擎"，而是 **故意只做图工程里 Org 那一半的平台** 。多 Agent 系统的大多数故障恰恰来自"谁拥有什么"模糊、上下文丢失、记忆不连续——这些问题它用长期 Thread + 关系 + 消息账本 + Topic 认真解决了。它把"动态工作流编排"留给各 Agent 自己的 Thread，这是一个清晰的产品边界，不是缺陷。

用公司的话说：CodexLoom 画好了组织架构图、建好了部门间的协作协议和审批流程，但不去编排每个项目的具体执行计划——它相信每个部门（Agent）自己有能力把活干好，治理层只负责"谁负责什么"和"什么时候需要人来做决策"。

# 结语：带着三把尺子离开

回到开头那句话：Graph Engineering = 把"关系"做成可查询、可计算、可治理、甚至可执行的工程体系。画图只是它的影子，不是它本身。

给实践者三条带走的建议：

**先 Loop，再 Graph** ：图的最小原子是循环，不是 Agent。就像一个公司，员工个人的"接到任务→做完→自查→交付"循环跑不稳，你把他放进任何项目流程里都只会制造混乱。连一个稳定的循环都做不好，就别急着连图。

**Verifier 才是真瓶颈** ：Worker 与 Verifier 绝不能共享上下文。就像质检员不能归生产部门管——否则质检标准只会越来越松。

**会判断"不用图"比"会画图"更高级** ：不是所有协作都该建模成图。CodexLoom 就是一个清醒的例子——它只做图工程里 Org 那一半，把动态工作流编排留给 Agent 自己的 Thread，因为有时候信任你的员工比微操他更有效。

最后，记住这把尺子。下次再看到"Graph Engineering"，先问自己三个问题：

```Plain Text
它说的是哪个范围（Scope）？   Work Graph 还是 Org Graph？
它说的是哪个系统平面（Plane）？ Control / Execution / Evaluation / Adaptation / Governance？
它说的是静态、动态生成，还是自适应修改（Dynamism）？=
```

三个问题答完，你对任何"Graph Engineering"的说法都能精确定位，不再被热词带着跑了。
